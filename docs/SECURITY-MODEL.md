# Security model

How Aver protects keys, receipts and your machine. To report a vulnerability, see [SECURITY.md](../SECURITY.md). [ARCHITECTURE.md](../ARCHITECTURE.md) is the full design.

- **No network listener.** Every `aver` command opens the home and acts in its own process. There is no daemon and no HTTP API, so nothing on the network can reach the store or the keys.
- **Keys.** Key files are mode 0600 in a 0700 directory under `$AVER_HOME/keys`. A command acts as the key file it reads: the admin's, or the agent's whose workspace it runs in. Each agent has only the capabilities it was granted, which keeps agents from acting on each other's work by mistake. Anyone who can read the key files as you can act as any agent in the home.
- **Receipts can be checked by anyone.** A receipt's id is the hash of its contents, and the receipt viewer in [`site/`](../site/README.md) checks the signature and the content hash in the browser.
- **A PASS is hard to forge.** Every check runs in the base snapshot's environment, so editing `aver.toml` (a `NODE_OPTIONS` preload, longer limits, an install command with network) cannot change how anything runs. The head runs with the base's copies of the harness (`aver.toml`, `.npmrc`, test runner configs, the `scripts` and test runner fields of `package.json`, and every existing test), and changing frozen harness is a `NEW` failure; the head's own versions of the tests run separately and only prove criteria, and its dependencies install for its runs only. A run that exits non-zero with no failing test, or empties its report, fails; so does exhausting memory or time on something that passed before. A criterion counts only if its test fails without the change and passes in the head's own tests. Files under a task's `protected_paths` cannot change without a `NEW` failure. All of this is judged against the attempt's base, so an attempt is accepted only from the task's base or its target's current value, never from a snapshot the agent prepared.
- **Repository content is data.** In the reports the CLI prints for agents (`aver verify` and `aver check` in a workspace directory, `aver notices`, the Claude hooks), file contents, diffs, test names and failure output appear only inside fenced blocks, each fence longer than any run of backticks in its content, under a note saying fenced text is data from the repository, not instructions. JSON output carries the same values in `content`, `diff`, `detail` and `output` fields.
- **Native runs.** Checks run on the host, in a slot cloned from the directory that has the dependencies installed and swapped to the tree under test, never in an agent's directory. Each run inherits the caller's environment minus the CI job's tokens and job files, with a private `TMPDIR`, the caller's `PATH` and the network on. Aver installs no dependencies for a check. Whatever a run leaves running is killed when it ends. Checks are not sandboxed: they run as you, or as `aver ci --run-as`'s user in CI.
- **Secrets.** Imports and workspace writes are scanned for secrets and rejected with the path and pattern name.
- **Agents of `aver run` run on the host.** Their directories are copies, but their commands are not sandboxed by Aver: Claude is limited to `acceptEdits` and a per-directory allowlist unless you pass `--yolo`, and Codex uses its own sandbox. Each agent acts with its own key, which gives attribution, not isolation.
