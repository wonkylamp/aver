Your agent says “done”. Aver checks.

Aver is version control built for AI agents. Agents work entirely in Aver, and a change only counts once it’s proven. Your team keeps Git: Aver hands it finished work.

Install How it works

Open source, MIT. A prototype for Node and TypeScript, Python, Rust and Go projects, on macOS and Linux, and on Windows through WSL2. Agents run on your machine as you. Their work is checked before it reaches you, and proven in CI.

Install

Needs macOS or Linux, git, your project's own toolchain, and an agent tool.

Claude Code

  1. Add the plugin, in Claude Code in the terminal or in the Code tab of the Claude desktop app:

    /plugin marketplace add wonkylamp/aver
    /plugin install aver@aver

  2. Install the aver command:

    curl -fsSL https://raw.githubusercontent.com/wonkylamp/aver/main/site/install.sh | sh

  3. In your repository:

    aver setup

The plugin adds the aver skill, /aver-run, /aver-check, /aver-verify and /aver-status, and finds aver even when the desktop app's PATH lacks ~/.local/bin. aver setup adds the worktree hooks, so claude --worktree <name> opens an Aver workspace.

AGENTS.md and other tools

  1. Install the aver command:

    curl -fsSL https://raw.githubusercontent.com/wonkylamp/aver/main/site/install.sh | sh

  2. In your repository, write Aver's instructions to AGENTS.md, which many agents read:

Any agent that can run shell commands uses the aver CLI directly.

Each command shows every file it will write in the repository and asks first. It writes only project-local files, never global configuration. aver setup sets up every tool it finds at once, and aver setup --remove undoes it.

To watch it first, run the demo. An agent hides the tests it broke and Aver says FAIL_OWN, a restore rewinds it, and the real fix gets PASS. It takes about 2 seconds, offline, and touches none of your repositories:

aver demo

Then check that everything Aver needs is there. It prints a fix for each problem:

aver doctor

Agents use Aver. Your team keeps Git.

Agents don’t use Git anymore. They use Aver. Every agent gets its own workspace, its own history, and merges that only happen when the work is proven. Your team keeps using Git, and Aver hands it finished work.

Agents, in Aver Your team, in Git
Where work happens Each agent gets its own instant workspace Your repo, unchanged
Saving progress Every change snapshotted in the agent’s own history Commits, as today
“It’s done” Only counts once it’s proven: each criterion has a test that fails without the change, nothing that worked broke, no test was weakened Arrives already proven, with a receipt
Working in parallel Agents are told when they touch the same files No collisions to untangle
Merging Merges only when everything merged together still passes Receives finished work as a branch or PR
What you do Nothing Review, merge and deploy as now

What Git gives people, Aver gives agents

Git was built for people who check their own work. Agents need the same ideas, rebuilt for many workers you cannot fully trust.

Aver doesn’t replace Git or GitHub. Your repo, branches and PRs stay as they are; Aver is where agents work, and only proven work reaches Git.

Three problems with agents today

  1. They say “done” when they aren’t.

    They delete or weaken the test that fails, or fix one thing and break another.

  2. Several at once is a mess.

    Worktrees are slow and heavy, and conflicts only show up at merge time.

  3. You become the bottleneck.

    You review every diff, because you can’t take an agent’s word for it.

Two everyday ways to use it

One agent, with a safety net

Give the task and say what done means. -c sets a criterion: the agent must add a test named with [crit:last-page] that fails without its fix and passes with it. It works in its own copy of the repository, so your working tree is never touched. When it passes, accept its work as a branch on the commit it started from, committed as you.

Already in Claude Code? After aver setup, claude --worktree <name> opens an Aver workspace with the same checks.

$ aver run "Fix the off-by-one in paginate()" -n 1 \
    -c "last-page: the last page lists the remaining items"
$ aver accept 1 --pr

Many agents, many tasks

Give Aver your open issues, or a file with one task per line, and it puts one agent on each, each in its own directory, so none overwrites another. When two change the same file, both hear about it while they work. The batch ends with one list: PASS is ready, FAIL_OWN broke something, REVIEW needs a person. The output below is from Aver's test suite, with scripted agents.

$ aver run --tasks tasks.txt

4 tasks · 1 ready · 1 broke something · 1 needs review · 1 unproven
#1 Add negate PASS     +3 -1    aver accept 1
#2 Add double FAIL_OWN broke "adds"
#3 Rename add REVIEW   changed 1 test expectation: aver diff 3
#4 Add triple UNPROVEN not proven: tri (passes_without_change)
overlap: #1 and #4 both change README.md (overlapping lines)
$ aver accept --all-pass --pr

How it's different from Git worktrees

A worktree is Git's own way to give each agent a checkout and a branch, and many parallel-agent tools are built on it. Aver workspaces keep that: each one has a Git view on its own branch, so git status, git diff and git commit work in it. What Aver adds is around the checkout.

  • Setup per agent. A worktree is a full checkout, then a fresh install, such as npm ci, in each one. An Aver workspace is a copy-on-write clone of one cached checkout, with dependencies linked from one shared store. Measured below.
  • Knowing it’s done. A worktree is done when the agent says so, and you or CI find out later. In an Aver workspace, aver check and aver verify tell the agent while it works, judged by the tests as the original has them.
  • Other agents. Worktrees are isolated until you merge, so collisions show up then. Aver tells agents about overlapping edits while they work.

Where a plain worktree is the better fit

  • Your project is not Node and TypeScript (npm), Python, Rust or Go. Aver verifies only those.
  • Your change is to a large Rust workspace. A verify builds both sides, so it takes minutes.

Neither one sandboxes the agent: under Aver, too, agents run on your machine as you.

How Aver decides whose fault a failure is

For a receipt, each test runs on the base and on the head, with the network off where the host allows. A failing side reruns up to three times and an infrastructure failure (the memory or time limit, or a runner error) is retried once. Then the first matching rule names the cause. Pick an example or press a run to change its result.

      The same receipt on every pull request

      Agents that do not run under Aver still open pull requests. The aver-verify GitHub Action runs both sides of each one on your own runners and posts the receipt as a comment. - div-basic: divide returns the quotient
- div-zero: divide throws on division by zero

      What broke, and was it the change?
      Every failing test gets a cause. Only a NEW failure is the pull request's fault; a test that already failed on the base is PREEXISTING and does not block.
      Did it do what was asked?
      A criterion is proven when a test tagged [crit:id] fails without the change and passes with it. An untested promise stays unproven.
      Did it cheat?
      Paths you mark protected, such as your tests, cannot change without a NEW failure. A test that ran on the base and vanished from the head is NEW too.

      Set up the GitHub Action

      The action runs on your own GitHub runners and posts one comment per pull request. It is new, so expect rough edges.

      1. Add the workflow

        Save this as .github/workflows/aver.yml. The example pins a tag for readability. Pin the action to a full commit SHA in your own workflow.

        on: pull_request
permissions:
  contents: read
  pull-requests: write
jobs:
  aver:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: wonkylamp/aver/action@v0.3.0

      2. Say what the pull request must do

        Add an aver block to the pull request description. Without one, Aver checks only that nothing broke.

        ```aver
- div-basic: divide returns the quotient
- div-zero: divide throws on division by zero
protected: test/**
```

      3. Tag the tests that prove it

        A test proves a criterion when its name contains [crit:id].

        test('[crit:div-zero] divide throws on division by zero', () => {
  assert.throws(() => divide(1, 0), /division by zero/);
});

      Questions

      Which projects does it work on?

      Node and TypeScript (npm), Python (pytest, with uv.lock or requirements files), Rust (Cargo) and Go. Aver finds each package and runs npm test, pytest, cargo test or go test in that ecosystem's pinned image, and an aver.toml at the repository root can pin the images, the installs and the checks. A change to files no check covers is never a pass.

      Which agents can aver run start?

      Claude Code and Codex, or any command-line agent through --agent-cmd. You can mix them in one run.

      Do the agents run in a sandbox?

      No. Each agent works in its own copy of the repository, but its commands run on your machine as you. Claude runs with an allowlist of commands unless you pass --yolo, and Codex uses its own sandbox. The proof runs natively too, in clean copies with a cleaned environment, the network off where the host allows, and no secrets.

      Can an agent prove a criterion with a weak test?

      Partly. A test that already passes without the change proves nothing, so an agent cannot tag an old test. But a test that only loads the new code still fails without the change and passes with it. Read the criterion tests, or give the task its own checks and protected paths, which the agent cannot change.

      Is this just comparing with the last CI run on main?

      No. Both sides run the same way, test by test. Failing tests rerun to catch flakiness. Existing tests run as the base has them, so editing a test cannot hide a regression. A criterion counts only if its test fails without the change.

      Does it replace Git?

      No. Aver imports commits from Git and exports the winning attempt as a normal branch whose parent is the commit the agents started from. Your working tree and current branch are not touched.

      What does the signature prove?

      The action makes a new verifier key for every run, so a valid signature shows the receipt has not changed since that run wrote it. It does not show who ran it. Running aver ci with a persistent --home keeps one key you can publish.

      What about pull requests from forks?

      GitHub gives them a read-only token, so they get no comment. The job summary and the uploaded receipt still carry the result. The action refuses to run on pull_request_target.

      Is it ready for production?

      No. Aver is a prototype. So far it has run on {{NUM:replay-total}} real pull requests and in two by-hand trials with real agents on a small package, and the evaluation on hard tasks is in progress. There is no hosted service.
