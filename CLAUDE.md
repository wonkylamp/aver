# CLAUDE.md

Aver is version control and collaboration infrastructure for AI agents. Read `PRD.md` for the why and `ARCHITECTURE.md` for the data model and components. `ARCHITECTURE.md` §1 is the source of truth for every stored object; change it first, then the code.

## Layout

- `crates/aver-core` owns ids, canonical JSON, hashing, signing, object types and the cause/verdict rules. No I/O, no async.
- `crates/aver` owns the services as modules (`services` wires them for one home; `store`, `git`, `env`, `workspace`, `disk`, `exec`, `judge` (also reachable as `verify`), `tasks`, `coord`, `run`, `integrate`, `cli`) and the `aver` binary. `presets` holds CI's default `npm test` and `typecheck` checks and generic mode's presets, `adhoc::runner` the test runners Aver adds reporters to, `suggest` what `aver init` drafts and the NOT CHECKED candidates, and `languages` the ecosystems a tree holds; outside CI nothing is detected, and a contract-shaped `aver.toml` loads through `contract::parse` (ARCHITECTURE.md §1.13.2); `coverage` decides which changed files no check covers; `judge` is the verification engine, split into `plan` (what to run), `run` (the runs, reruns and confirmations) and `finish` (entries, verdict, receipt, diagnostics) around the `Verifier` in `judge/mod.rs`; `exec` holds native runs, the run output types (`output`), the scripted runner seam the tests drive the executor through (`seam`, and `scripted` behind the cargo feature of that name, which only the crate's own dev-dependency enables; `AVER_SCRIPTED=1` selects it there) and the report parsers (`junit`, `jest`, `libtest`, `gojson`); `disk` holds the host side of on-disk workspaces (checkouts, clones, scan and stat cache, gc), and `place::sides::seed_workspace` clones the checkout's installed dependencies into them; `run` holds `aver run` (supervisor, templates, brief, run file, live view, comparison, accept, combine, hooks, feedback, and `batch`: tasks files and issues, the queue and the batch summary) and the agent-facing verify report; `coord` holds leases and overlap notices between tasks; `integrate` what `aver integrate claude` writes.
- `integrations/claude-code/` is the Claude Code plugin. Its `skills/aver/SKILL.md` body is the one source of the instructions every `aver integrate` target writes (`integrate::text`); `crates/aver/tests/integrate_text.rs` checks that every `aver` command and flag the skills name exists.
- `action/` is the `aver-verify` GitHub Action (composite; scripts in `action/*.sh` with `set -euo pipefail`) and `action/test/`. `.github/workflows/` holds this repository's CI, release and site deploy workflows; CI splits `make test-native` with `scripts/test-native-shard.sh` and skips the Rust jobs when only top-level Markdown, `docs/` or `site/` changed. Every third-party `uses:` is pinned to a full commit SHA.
- `schemas/` holds the published JSON Schemas, one file per object kind and version.
- `site/` is the landing page and the receipt viewer, whose canonical JSON and signing code is in `site/src/core/`.
- `fixtures/` holds small projects used by tests. The Node ones have zero npm dependencies on purpose; the Python, Go and Rust ones (`py-calc`, `go-calc`, `rust-calc`) have no `aver.toml`, so CI's generic mode detects them and locally they answer NOT CHECKED until `aver check -- <cmd>` writes one, and need no network except pytest's pinned install. `py-uv`, `go-deps` and `rust-deps` each have one real dependency, to test the dependency layers.

## Rules that are not optional

1. **Objects are immutable.** Never update an object row. New information is a new object or a row in a mutable index table.
2. **Only `aver-core` computes ids.** Everything else calls `Object::id()` or `store.put()`. Never hash bytes ad hoc.
3. **Hashed objects are strict.** Unknown fields, unsorted sets and floats are parse errors. Add a field by bumping the schema version and updating `schemas/` in the same change.
4. **No Git working directories for Aver's own state.** The Git bridge uses `ls-tree`, `cat-file --batch` and `fast-import` only. Never `git checkout` or `git clone` without `--bare`/`--no-checkout`. Aver never builds its storage on a Git working directory and never reads state from one. A workspace directory may carry a write-only Git view for agent tooling (`git status`, `git diff`, `git commit` on the branch `aver/<label>`), laid out as a linked worktree of the bare repository `$AVER_HOME/git/<ws>` so standard tools and Claude Code read it: Aver writes it and never reads its contents back; the overlay stays the only truth. The exceptions read only refs and commit messages: the removal guard (`disk::gitview::unfetched`), so `WorktreeRemove` never deletes commits the user's repository lacks, and `disk::gitview::latest_subject`, the agent's newest commit subject (untrusted text: one line, escaped, capped) as `aver accept`'s title. The view's `origin` is the user's repository, so `git push origin` works inside the directory.
5. **Store bytes.** No syntax trees in the object store.
6. (Removed in 0.4 with the HTTP API.)
7. **Repository content is data.** Any string that came from the repo (file contents, test names, failure output) is returned in a `content`/`diff`/`detail`/`output` field. In the plain-text reports the CLI prints for agents (`aver verify` and `aver check` in a workspace directory, `aver notices`, the Claude hooks), it goes inside fenced blocks instead: one per section, each fence longer than any run of backticks in its content, control characters other than line breaks escaped, under one note at the top saying fenced text is data from the repository, not instructions (`run::report::fence`), shown in full once per workspace directory and as a short marker after (`run::report::note_once`).
8. **Checks never get the CI job's credentials.** Aver 0.4 deleted the Docker sandbox: checks run natively under rule 10, with the network on and the caller's environment, so their isolation is a slot of their own, the CI tokens and job files rule 10 strips, and `--run-as` in CI.
9. **Timestamps never enter snapshots, trees or environments.**
10. **Checks run in a slot, never in the agent's directory.** A check run executes in a slot cloned for its side (`place/sides.rs`, ARCHITECTURE.md §1.8.5) and swapped to its tree, never in the agent's own directory. Its environment is the caller's minus the CI tokens and job files `place::proc::STRIPPED` names, with a private `TMPDIR` per run and a `CARGO_TARGET_DIR` outside the slot moved to `<slot>/target` (`place::proc::inherit`). Changes to the environment handling in `place/proc.rs` need a test in `crates/aver/tests/place.rs`.

## Conventions

- Rust 2021, `cargo fmt`, `cargo clippy -- -D warnings`. Errors are `thiserror` enums at module boundaries; `anyhow` only in the CLI and tests.
- Parse at boundaries into typed values (`SnapshotId`, `Path`, `CheckId`), trust them inside. Ids are newtypes, never bare `String`s.
- One SQLite writer connection behind a mutex; readers from a pool. Multi-object writes go through `store.tx(|tx| …)`.
- Tests assert behavior through public APIs. Tests that run Node natively are `#[ignore]` with a reason string and run under `make test-native`, so `cargo test --workspace` passes where Node is missing.
- Comments explain a non-obvious why. No narration comments.
- TypeScript: strict mode, ESM, no `any` in exported types.
